# Changelog: week of 2026-10-12 (Mon) – 2026-10-18 (Sun)

## ChebyshevT: real-only MPFR recurrence branch (arbitrary-precision real speedup) ; v0.357

**A cross-system stress test of `ChebyshevT` confirmed it correct and highly
efficient in every numeric regime, and exposed one clean arbitrary-precision
perf win, now closed.** The test ran 50 argument probes across machine
real/complex and arbitrary-precision real/complex — integer/negative/non-integer
and complex order, cancellation, branch-cut edges, and special values — against
SciPy `eval_chebyt`, SymPy `chebyshevt`, mpmath `chebyt` and wolframscript
(Wolfram Engine 14.0), scored against a 260-digit mpmath oracle.

- **Correctness: 0 disagreements.** Every class-A probe matched the oracle in all
  four regimes (one fully-exact complex-order call stays symbolic by design).
  Mathilda is *more* accurate than Wolfram on the hard machine-complex cases
  (`ChebyshevT[1000, 0.3 + 0.1 I]`: ~6 ULP vs WL ~2180 ULP; exact `0` at
  `T_49(0)` where WL carries ~8e-15 roundoff) and far more accurate than SciPy,
  whose complex `eval_chebyt` is wildly inaccurate (10²¹–10²⁸ ULP off) for
  arguments away from `[-1, 1]` — not a Mathilda issue, but it rules SciPy out as
  an oracle for the complex regimes.
- **Cross-surface bit-identity.** Scalar == unpacked List == packed List ==
  `NDArray` == `Compile[]` to the last bit, for machine real and complex argument
  at integer orders straddling the fast-path edge (n = 50, 1000, 1001); all four
  `Compile[]` shapes report `Compiled -> True`.
- **Efficiency.** Machine real ~11 ns/element (≈5× NumPy's `eval_chebyt`, ≈228×
  wolframscript); machine complex ~20 ns/element (≈25× NumPy). Arbitrary
  precision was within ~2.3–2.4× of mpmath — both on GMP/MPFR, so core-vs-core
  (wolframscript wins the arb-prec scalar via an `O(1)` closed form; matching that
  is a documented follow-up, not a kernel gap).

**The fix (`src/special_functions/chebyshev_t.c`, `cheb_numeric_recurrence`).**
The arbitrary-precision three-term recurrence always ran in complex `ncpx`
arithmetic, even for a purely real argument — paying for an always-zero imaginary
part on every one of the `n` steps (two real multiplies and a handful of
real add/sub per complex multiply that do nothing). The recurrence now branches
on `mpfr_zero_p(x.im)`: a real argument runs a plain `mpfr_t` recurrence (`r_k =
2 x r_{k-1} - r_{k-2}`), and only a genuinely complex argument takes the `ncpx`
path, which is **byte-for-byte unchanged**. **A/B-measured ~7–8% faster** on real
arbitrary-precision evaluations (`ChebyshevT[1000, 1/3]` at 200 digits: 1873 →
1722 ms over 100 distinct inputs; `ChebyshevT[2000, ·]` at 300 digits: 3580 →
3333 ms), with the complex regime and all machine regimes untouched. Accuracy is
identical (the real and complex recurrences compute the same real value; the
complex path merely carried a zero imaginary part through). No new builtins,
attributes, or API; no `pack.c` / `compile_*` / ND-kernel edits (the change is
below the machine fast path). `chebyshev_t_tests` green, `check-nd-surfaces`,
`check-compile-coverage`, `check-array-exactness`, `check-packed-aware`,
`check-c99`, `check-messages` pass, valgrind reports no new leaks.
