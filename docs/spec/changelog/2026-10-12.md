# Changelog: week of 2026-10-12 (Mon) – 2026-10-18 (Sun)

## LaguerreL: Laguerre and generalized Laguerre polynomials ; v0.374

New builtin `LaguerreL[n, x]` (Laguerre polynomial `L_n(x)`) and `LaguerreL[n,
a, x]` (generalized `L_n^(a)(x)`, with `LaguerreL[n, x] == LaguerreL[n, 0, x]`),
to the ChebyshevU bar — symbolic, numeric, packed/NDArray, and `Compile[]`.

- **Exact polynomial.** A non-negative integer order yields the explicit
  polynomial: exact rational coefficients via the three-term recurrence for a
  numeric/absent parameter `a`, and the expanded polynomial in `a` and `x` for a
  symbolic `a`. `LaguerreL[5, x] = 1 - 5 x + 5 x² - 5/3 x³ + 5/24 x⁴ - 1/120 x⁵`,
  `LaguerreL[2, a, x] = 1 + 3/2 a + 1/2 a² - 2 x - a x + 1/2 x²`,
  `Table[LaguerreL[10, x], {x, 1, 5}] = {168919/403200, -4381/14175,
  -31361/44800, 931/675, 254927/145152}`.
- **Numerics.** Integer order with an inexact argument uses the *stable*
  recurrence rather than polynomial substitution, so `LaguerreL[100, 0, N[5,
  20]] = 1.4555271625328812607` instead of the catastrophically-cancelled
  `1.4557…`. Non-integer / complex order evaluates through the entire form
  `Binomial[n+a, n] Hypergeometric1F1[-n, a+1, x]` — machine or MPFR, real or
  complex: `LaguerreL[6., 5] = -2.09028`, `LaguerreL[6. - I, 5] = -2.76039 -
  2.46853 I`, `LaguerreL[2.5, 1.3, 8 + I] = 8.50391 + 0.576867 I`,
  `N[LaguerreL[2/5, 1/3, 8/7], 50]` to 50 digits.
- **Special values.** `LaguerreL[0, x] = 1`, `LaguerreL[n, 0] = Binomial[n+a,
  n]` (= 1 for the ordinary polynomial).
- **Derivative.** `D[LaguerreL[n, x], x] = -LaguerreL[n-1, 1, x]`;
  `D[LaguerreL[n, a, x], x] = -LaguerreL[n-1, a+1, x]`.
- **Fast paths.** A binary ND kernel (`sf_machine_laguerre_l[_c]`) gives the
  two-argument form NDArray + packed + `Compile[]` + auto-compilation, with a
  machine-complex arm; the scalar machine path dispatches to the same helper, so
  scalar == List == packed == NDArray == `Compile[]` bit-for-bit. The generalized
  three-argument form adds an N-ary kernel for scalar `Compile[]`.
- **Attributes.** `Listable`, `NumericFunction`, `Protected`. Diagnostics route
  through `mth_message` (`LaguerreL::argt`).

New: `src/special_functions/laguerre_l.{c,h}`, `tests/test_laguerre_l.c`.
Touched: `src/special_functions/sf_machine.{c,h}`, `src/ndkernels.c`,
`src/calculus/deriv.c`, `src/sym_names.{c,h}`, `src/core.c`, `src/info.c`,
`src/version.h`, `tests/CMakeLists.txt`. Spec:
`docs/spec/builtins/special-functions.md`.

## Series: parametric arguments & branches at infinity — 12 more gaps closed ; v0.373

Extends the assumption-aware `Series` work (v0.368) to scaled/parametric
arguments and directional branches at infinity, from a 50-case stress set. All
verified against a per-case oracle; no new `series`/`limit` regressions.

- **`ArcTan[c x]` honours the coefficient sign.** `Series[ArcTan[a x], {x, Infinity, 1}, a < 0]`
  = `-Pi/2 - 1/(a x)` (the argument runs to `-Infinity`), not the old `+Pi/2`.
  Fixed where the `so_apply_arccot` branch emits the constant; composes with the
  `-Infinity` reflection (so the `{x, -Infinity, 1}` twins flip correctly too).
- **Parametric (scaled) arguments at infinity.** A new preprocessing step maps a
  head `H[c x]` (homogeneous linear, `c` sign known) to its bare-variable
  asymptotic:
  - Saturating heads limit to a sign-dependent constant: `Erf[c x] -> Sign[c]`,
    `Tanh[c x] -> Sign[c]`, `Erfc[c x] -> 0`/`2`, `FresnelS`/`FresnelC[c x] -> ±1/2`
    (order 0). Previously all returned unevaluated.
  - Growth/decay heads carry the scaled asymptotic: `ExpIntegralEi[a x] -> E^(a x)/(a x)`,
    `ExpIntegralE[1, a x] -> E^(-a x)/(a x)` (`a > 0`).
- **`ArcCosh[c x]`/`ArcSinh[c x]` take the correct branch for `c < 0`** via the
  reflections `ArcCosh[c x] = I Pi + ArcCosh[-c x]`, `ArcSinh[c x] = -ArcSinh[-c x]`
  (a fresh variable avoids `odd_fold` cancelling the `ArcSinh` reflection).
  `Series[ArcCosh[a x], {x, Infinity, 1}, a < 0]` now gives the upper-half-plane
  `I Pi + Log[-2 a x] + ...` (was the wrong `-I Pi` branch).
- **New `ExpIntegralE[1, x]` at-infinity emitter** (DLMF 6.12.1):
  `E^(-x)(1/x - 1/x^2 + 2/x^3 - ...)`, the decaying `E^(-x)` kept symbolic.

All in `src/calculus/series.c` (an `ArcTan` branch fix in `series_expand`, a
parametric-argument block + two new emitters in `do_series_single`). Spec:
`docs/spec/builtins/power-series.md`. Tests: `tests/test_series_assumptions.c`.

## Notebook: select part of a StandardForm result and reuse it as input ; v0.369

Typeset output is now selectable, Mathematica-style. In a StandardForm result a
click selects the innermost subexpression under the pointer, a click inside the
selection widens it to the enclosing one (repeat to reach the whole result; one
more click starts again), and a drag snaps to the smallest subexpression covering
it. Cmd/Ctrl+C — or *Copy Selection as Input* on the right-click menu — copies the
selection's **InputForm**, so it pastes straight into an input cell.

- Kernel: `expr_to_latex_selectable` (`src/print_latex.c`) wraps every rendered
  subexpression in `\htmlData{mp=K}{...}` and returns each one's InputForm; the
  pipe protocol and FFI send them as `"sparts": [...]` beside `slatex` (part 0 is
  the whole result). Budgeted at 4096 subexpressions / 256 KB of part text — a
  larger result is sent untagged, and a bounded node count skips it up front.
- A denominator's reciprocal is now one subexpression in StandardForm, so
  `Sqrt[2 + y]` in `(1 + x)/Sqrt[2 + y]` (and `x^2` in `a/x^2`) selects as a whole.
- Fix (both notations): a radical no longer brackets its body —
  `Sqrt[1 + x]` was typeset as √((1+x)), now √(1+x); likewise `(1 + x)^(1/3)`.
- Front end: `frontend/src/lib/mathSelect.ts` (a Svelte action) does the
  selection and copy; the highlight is drawn as a box over the selection's glyphs,
  so it covers a whole fraction or radical. KaTeX is trusted with `\htmlData`
  only (data attributes; nothing that can link, style or script).
- Tests: `test_selectable_standardform`, `test_radical_body_unbracketed`
  (`tests/test_print.c`); five `sparts` cases in `tools/check_pipe_protocol.py`;
  two wiring checks in `frontend/scripts/check-notebook.mjs`. Selection driven in
  headless Chrome over real kernel output (click/widen/restart, drag, copy, Escape).

## Series: assumption-aware branch selection — 7 gaps closed ; v0.368

`Series[..., Assumptions -> ...]` now actively monitors the domain of the
expansion variable and symbolic parameters to pick the correct branch, closing
seven cases from an assumed-series stress set (all verified against a 30-case
oracle; no regression across 21 series/Simplify/Refine/assumption suites).

- **Non-analytic heads resolved at the expansion point.** `Abs[g]`, `Sign[g]`,
  `UnitStep[g]` now choose their branch from the sign of `g` **at** `x0` when the
  generic sign is undecidable in `x` (they are locally smooth where the argument
  is nonzero). The sign query at the point goes through the Reduce/CAD bridge, so
  a compound value such as `-a` or `b - c` is decided — not just a bare signed
  symbol. `Series[Abs[x - a], {x, 0, 2}, Assumptions -> a > 0]` = `a - x`
  (`x - a` for `a < 0`), previously a `Derivative[Abs][-a]` husk.
- **Even-order roots under `x < 0`.** When the radicand vanishes to an even order
  at the origin, the leading monomial reduces as `|x|^e`, so an odd extracted
  exponent flips the whole series for `x < 0`:
  `Series[Sqrt[1 - Cos[x]], {x, 0, 2}, Assumptions -> x < 0]` = `-x/Sqrt[2]`, and
  `Series[Sqrt[x^4 + a x^2], {x, 0, 3}, Assumptions -> a > 0 && x < 0]` =
  `-Sqrt[a] x - x^3/(2 Sqrt[a])`. The "hidden square" generalization of the
  explicit `Sqrt[x^2] -> ±x` handler.
- **`Sqrt` of a provably-negative quantity → imaginary branch.** A new rule in
  the shared `apply_assumption_rules`, `a^(p/2) -> I^p (-a)^(p/2)` for `a < 0`
  (so `Sqrt[a] -> I Sqrt[-a]`, `1/Sqrt[a] -> -I/Sqrt[-a]`), also improves
  `Refine`/`Simplify` under negativity assumptions.
  `Series[Sqrt[a - x], {x, 0, 1}, Assumptions -> a < 0]` =
  `I Sqrt[-a] + (I/2) x/Sqrt[-a]`.
- **Expansion at `-Infinity`.** Handled by reflection `x -> -x` onto the existing
  `+Infinity` machinery, reported in the canonical `1/x` variable:
  `Series[Sqrt[x^2 + a x], {x, -Infinity, 1}, Assumptions -> Element[a, Reals]]`
  = `-x - a/2 + a^2/(8 x) + O[1/x]^2` (its `+Infinity` twin with odd-exponent
  terms sign-flipped). Previously unevaluated, with spurious `Infinity::indet`
  warnings — now gone, since `-Infinity` never reaches the finite-`x0` arithmetic.

Kernel: `src/calculus/series.c` (non-analytic block, Power arm, and a new
`series_is_neg_infinity` reflection path in `do_series_single`) and one rule in
`src/simp/simp_assume_rewrite.c`. Series is structural (returns `SeriesData`), so
no packed/NDArray or `Compile[]` surface is involved. Spec:
`docs/spec/builtins/power-series.md`. Tests: `tests/test_series_assumptions.c`.

## Notebook: StandardForm (Mathilda names, Arial) and TraditionalForm ; v0.367

The notebook's typeset output used to be textbook notation (`\sin(x)`, `\ln(x)`,

## Limit: two-term special-function asymptotics (sub-leading probes) ; v0.366

A third, deeper parametric stress set surfaced a correctness bug in the v0.365
special-function asymptotics: the single-term Hurwitz-Zeta and incomplete-Gamma
rewrites returned a WRONG `0` when an expression subtracts the leading term to
probe the next order. Fixed by carrying a second asymptotic term:

- `Zeta[s, q] ~ q^(1-s)/(s-1) + q^(-s)/2`, so
  `Limit[x^s (Zeta[s, x] - 1/((s-1) x^(s-1))), x -> Infinity, Assumptions -> s > 1] = 1/2`.
- `Gamma[s, z] ~ z^(s-1) Exp[-z] (1 + (s-1)/z)` (written factored so the leading
  factor still folds), so
  `Limit[x (Gamma[a,x]/(x^(a-1) Exp[-x]) - 1), x -> Infinity] = a - 1`.

Leading-order cases those rewrites also serve (`x^(a-1) Zeta[a,x] -> 1/(a-1)`,
`x^(2-2a) Exp[x^2] Gamma[a,x^2] -> 1`) are unchanged, and both are now locked as
guards in `tests/test_limit_assumptions.c`. The deeper residual classes in that
stress set (parametrized high-order Taylor residuals, Stirling series beyond two
terms, Beta/PolyGamma tracking, branch cuts at `-Infinity`) remain open — they
need a general symbolic small-argument/asymptotic series, a larger piece of work.
Note: several cases in that set carry incorrect expected values (Mathilda is
right) — e.g. `(Log[1+a x] - Sin[a x] + a^2 x^2/2)/x^3 -> a^3/2` (not `a^3/3`),
`(Exp[a x]-1-a x)/(1-Cos[b x]) -> a^2/b^2` (not `2a^2/b^2`).

## Limit: generalize the assumption machinery (held-out stress set) ; v0.365

A second, harder 50-case parametric stress set (held out to check the v0.364 work is
algorithmic, not overfit) went from 28/50 to 46/50. All work is in
`src/calculus/limit.c` plus a second locked corpus + regression guards in
`tests/test_limit_assumptions.c`. Every new layer is assumption- or shape-gated and
NULL on uncertainty; leading-term asymptotic folds are sound for a limit (the dropped
tail vanishes relative to the leading term) and are guarded so an enclosing factor
cannot amplify a dropped sub-leading term.

- **Opaque-head limits before the opaque gate**: Floor/Ceiling/Round/IntegerPart
  asymptotic in a product whose other factors vanish (`x Floor[a/x] -> a`,
  `Floor[t]/t -> 1`); FractionalPart (bounded) times a vanishing factor; `Mod[a, x] -> a`.
- **Small-argument linearization** (late fallback): `H[g] ~ g` for `g -> 0` and H in
  the Sin/Tan/Sinh/ArcTan/... ~identity family (`x^a Sin[b/x^a] -> b`). Placed after
  Series so it never overrides an exact expansion.
- **Log of a finite-nonzero sum**: a buried `Log[x^a + y^a]` (a<0) folds to `Log[y^a]`,
  so `Log[x^a + y^a]/Log[x] -> 0`. Gated to a Plus argument and to `Log[L] != 0`.
- **Exponential decay by an ordering fact**: the rate is now the slope `D[arg, x]`
  (a constant intercept is harmless), and a real rate whose sign is an ordering fact
  (`b > d`) is read by `exponent_sign_ctx` — but only to strengthen a *decay* verdict,
  so a growth case the real/complex phase cannot be decided for still abstains.
- **Integrand Refine under assumptions**: `Sin[a Pi + x]` with `a in Integers` reduces
  to `(-1)^a Sin[x]` before the cascade (a one-time top-level `Refine`).
- **Abs of a complex argument**: `Abs[x + I a]` folds to `Sqrt[x^2 + a^2]` via
  `ComplexExpand`, so `Abs[x + I a] - x -> 0` and `x (Abs[x + I a] - x) -> a^2/2`.
- **More special-function asymptotics**: Erfc `~ Exp[-z^2]/(z Sqrt[Pi])`, incomplete
  `Gamma[s, z] ~ z^(s-1) Exp[-z]`, small-argument `BesselY`, and the full Stirling
  `Gamma[z] ~ Sqrt[2 Pi] z^(z-1/2) Exp[-z]` (as an explicit power/exp rewrite resolved
  by the log-reduction layer — Series is never applied to Gamma, so the tower hang is
  not reached).
- **Affine exponent sign**: `exponent_sign_ctx` now signs `A + k` (k a numeric literal)
  from `A` vs `-k` (so `x^(a-1) -> 0` under `a < 1`).

Remaining open on the held-out set: a parameter-transitivity case (`c > a > 0 => c > 0`,
an oracle-level gap) and one deep Stirling-class tower; two further source cases carry
incorrect expected values (an `a x^2` that cancels; an `x -> -Infinity` surd whose true
value is `-a`). Verified: both 50-case corpora green, limit/gruntz/series/integrals
suites regression-clean, valgrind byte-identical to the startup baseline.

## Limit: close 15 assumption-aware parametric gaps (Groups A–G) ; v0.364

`Limit` already honoured `Assumptions ->` / `Assuming[]` / `$Assumptions` via the shared
`AssumeCtx` solver; this pass closes the remaining parametric gaps so a 50-case assumed-limit
stress corpus goes from 35/50 to 50/50. All work is in `src/calculus/limit.c` plus the locked
corpus and guard tests in `tests/test_limit_assumptions.c`. Every new layer is assumption- or
shape-gated and returns `NULL` on any uncertainty, so a `NULL` `AssumeCtx` reproduces the legacy
path byte-for-byte. No `src/calculus/series.c` change (a `SeriesData` cannot carry the symbolic
exponents these shapes need, and a Gamma series hook would reintroduce the documented tower hang).
No numeric/packed/`Compile[]` surface is implicated — the changes are symbolic.

- **Product dominance** (`layer_dominant_product`, three shape-gated arms, after
  `layer_bounded_envelope`): a power beating a logarithm (`x^a Log[x] -> 0`), a geometric decay
  beating a polynomial (`x a^x -> 0`, `0 < a < 1`), and a vanishing factor times a bounded
  oscillation (`x^a Sin[1/x] -> 0`). A genuinely indeterminate `0 * Infinity` is left to Gruntz;
  the bounded-ness test is sound (does not rely on `magnitude_upper_bound`, which is a *lower*
  bound for negative powers).
- **Exponential decay by complex part** (`layer_exp_decay_re`): `E^(c t) -> 0` at `t -> ±Infinity`
  when `ComplexExpand[Re[c]]` is signed negative by the oracle — `Exp[-w t]` (`Re[w] > 0`) and
  `Exp[I w t]` (`Im[w] > 0`).
- **Symbolic-power log asymptotics**: `Log[x^a + 1] ~ a Log[x]` (`a > 0`) is now recognised for a
  symbolic exponent, including inside a quotient (`Log[x^a + 1]/Log[x] -> a`), by an
  assumption-aware branch of the dominant-`Log`-summand rewrite plus a subterm pass.
- **Negative-exponent monomial substitute**: `1/(x^a + 1) -> 1` for `a < 0` (`x^a -> 0`), the
  mirror of the existing `a > 0` arm.
- **Step functions one-sided at an integer** (`try_step_function_onesided`, before the opaque-head
  gate): `Floor`, `Ceiling`, `Round`, `IntegerPart`, `FractionalPart` at an integer point (a
  literal, or a symbolic `a` with `Element[a, Integers]`). Keyed on the *inner* limit being an
  integer, so `Floor[2x]` at `x -> 3/2` works too. Two-sided or non-integer points stay unevaluated.
- **Special-function leading asymptotics** (`layer_special_fn_asymptotic`, before continuous
  substitution — which doubles as the Gamma firewall): Gamma ratio `Gamma[x + a]/Gamma[x] -> x^a`
  (rewritten to a pure power, so no Gamma tower reaches `Series`/Gruntz), Hurwitz zeta
  `Zeta[s, q] ~ q^(1-s)/(s-1)`, and small-argument `BesselJ[nu, z] ~ (z/2)^nu/Gamma[nu+1]`.

Verified: 50/50 on the stress corpus; regression-clean across the limit suites, `gruntz_tests`,
`series_tests`, `integrals_tests`, `integrate_newton_leibniz_tests`; valgrind leak totals
byte-identical to the startup baseline.

## Hash: integer hash codes for expressions (`"Expression"` type) ; v0.363

New builtin `Hash[expr]` / `Hash[expr, type]` / `Hash[expr, type, "format"]`, in the
`ByteCount` / `LeafCount` family (`src/core.c`, `Protected`, documented in `src/info.c` and
`docs/spec/builtins/expression-information.md`; `SYM_Hash` interned in `src/sym_names.c`).

This first cut implements the default `"Expression"` hash type only: it surfaces the system's
existing 64-bit FNV-1a structural hash (`expr_hash`) — already the keying primitive for
Associations, memo tables and like-term grouping — to the REPL. The argument is evaluated
first (`Hash[1 + 1] == Hash[2]`), and the result is a non-negative integer (a bigint when it
exceeds `2^63 - 1`). As in Mathematica the value is implementation-defined and may differ
between systems and versions.

- **Formats** for `Hash[expr, "Expression", "format"]`: `"Integer"` (default), `"DecimalString"`,
  `"HexString"` (16 lowercase hex digits, big-endian), `"HexStringLittleEndian"`, and
  `"Base36String"`.
- **Left unevaluated for now** (no message, so `Quiet[]`/`Check[]` stay correct): non-`"Expression"`
  hash types (`"SHA256"`, `{"SHA", b}`, `"MD5"`, `"CRC32"`, …), the `"ByteArray"`/`"Base64Encoding"`
  formats (no `ByteArray` type exists yet), non-string type/format arguments, and wrong arg counts.
- Not `Listable`: `Hash[{1, 2, 3}]` hashes the whole list.

Tests in `tests/test_hash.c` (11 groups): determinism, argument evaluation, structural
sensitivity, format round-trips (`FromDigits[Hash[x, "Expression", "HexString"], 16] == Hash[x]`),
direct-C exact cross-checks of every string format (pinning the little-endian byte order), the
bigint-return path, and the stays-unevaluated cases. Valgrind-clean (leak profile identical to a
sibling test — only the fixed macOS platform-runtime startup baseline).

## Integrate / PossibleZeroQ: no spurious `Power::infy` from internal verification probes ; v0.362

`Integrate[1/Sqrt[Coth[x]], x]` returned the correct antiderivative but leaked two
`Power::infy: Infinite expression 1/0 encountered.` lines (Nasser-style report).
The integrator verifies candidates by numeric sampling, and a sample landing on a
pole of the candidate forms `1/0`. That diagnostic is sampling noise, but it was
**not cosmetic**: because the message was *noted*, `Check[Integrate[1/Sqrt[Coth[x]],
x], MARKER]` returned `MARKER` — the failure branch — for a successful integral.

**Root cause: `PossibleZeroQ`'s sampler did not mute its throwaway samples.** The
integrator's proper verifier (`differentiates_back`) uses `PossibleZeroQ`, whose
Schwartz–Zippel sampler in `src/zero_test.c` evaluated each sample point with no
arithmetic-warning mute — so a pole sample leaked. A bare `PossibleZeroQ[…]` on a
pole-bearing expression leaked identically. The per-sample evaluator `evaluate_rung`

## DSolve: an automatic answer is a solution — no series, no y', no probe noise (Nasser's v0.354 report) ; v0.361

**Nasser Abbasi reported seven DSolve deficiencies in v0.354; all seven are
addressed.** Root causes and fixes:

- **Series answers nobody asked for (item 1).** `DSolve`FrobeniusSeries` and its
  shifted-ordinary-point fallback were the last methods in the automatic cascade, so
  `(3x-1) y'' - (3x+2) y' + (6x-8) y == 0` came back as `C[1] + C[2] x + … + O[x]^7`.
  Mathematica's `DSolve` never returns a truncated series. The series methods are now
  **opt-in** (`Method -> "PowerSeries" | "FrobeniusSeries"`, or the direct builtins),
  and an ODE with no closed form found stays unevaluated. (This ODE is Kummer with
  `b = -1` after an exponential shift, the degenerate logarithmic case; a closed form
  needs `HypergeometricU` numerics and derivatives, which is follow-up work.)
- **`+ -1/6 (…) x^3` in the series display.** `series_build_term` (`print.c`) built
  `Times[Times[-1/6, …], x^3]`, and the Plus printer reads a summand's sign only off
  its leading Times factor. A product coefficient is now spliced into one flat
  `Times`, so the output is `- (C[2] + 4 C[1]) x^2 - 1/6 (…) x^3` (TeXForm too).
- **Answers carrying `y'` (items 3–7).** `DSolve`ReducibleFirstIntegral` returned the
  first integral `F(y, y') == C[1]` (a reduction of order, not a solution) and ran
  ahead of the autonomous implicit companion, which answers the same equations in x
  and y alone. It is now **pinned-only**. A dispatcher backstop also turns any
  automatic answer containing `SeriesData` or a derivative of the unknown into
  "unevaluated". The backstop can only decline; it never substitutes another answer.
  The autonomous reduction also produces better answers:
  - **Stage-1 normalisation.** `E^(c (C[2] + d Log[y]))` is split to `E^(c C[2]) y^(c d)`,
    and a constant occurring only as `E^(α_i C[k])` is absorbed into a renamed
    `C[k]`. `y y'' == b + a y'^2` now gives
    `∫ -2a/Sqrt[-4a(b - 2 C[2] a y^(2a))] dy - x == C[1]`.
  - **The implicit companion attempts the quadrature** (2 s, derivative re-checked).
    `y^2 y'' == a` now returns the elementary
    `y Sqrt[C[2] - 2a/y]/C[2] + 2a ArcTanh[Sqrt[C[2] - 2a/y]/Sqrt[C[2]]]/C[2]^(3/2) - x == C[1]`.
  - `z'' + z^3 == 0`, `y y'' == b + a y'^2`, `1 + y'^2 + 2 y y'' == 0` and
    `3(1-y) y y'' == 2(1-2y) y'^2` return inert-quadrature relations in x and y.
    Elliptic and ₂F₁ closed forms, and an `Integrate` gap on `k y/Sqrt[k y - k² y²]`
    for case 5, are follow-up work.
- **Leaking `Integrate::nonelem` / `Solve::nongen` (items 2, 6).** A nested `DSolve`
  (a method's speculative sub-solve) now runs as a muted *probe region*. Its
  diagnostics are neither printed nor seen by an enclosing `Check[]`; the new
  `mth_msg_fired_restore` rolls back the firing counter. `DSolve`Homogeneous` also
  mutes its v-quadrature, as Separable already did.
- **False homogeneity (item 2).** `ds_free_of` tests `D[e, x] == 0` with the numeric
  zero test, and `PossibleZeroQ[2 a v Csch[v x]^2]` is True (the decay false
  positive), so `Coth[v x]` passed as free of x. A numeric "zero" that is not
  structurally zero is now confirmed at a moderate exact-rational point.

**Corpus impact (same-machine A/B against HEAD, every changed record re-classified on
the HEAD binary):** 366 PASS→UNEVAL = 337 series + 22 y'-first-integrals + 7 masked
WRONG answers (the `ds_free_of` fix; residuals −0.44 / 1.48 that the harness had
passed); 15 UNEVAL→PASS; **0 new FAIL**. Gate baselines were raised by exactly the
attributable delta. The newly-unsolved records are the work list in `DSOLVE_PLAN.md`
M68.

Tests: new `t_nasser_*` regressions (intrinsic implicit-function verification of each
autonomous answer, `Check[]` silence, series sign display). Existing tests now pin the
series or first-integral Method where they asserted those shapes. Thirty residual
checks that substituted with applied-form rules (`y[x] -> …`, which leaves `y'[x]` in
the residual, so they had been passing vacuously) now use the pure-function form.

## Compile: Chop and Clip lower over rank-1 arrays ; v0.360

`Chop` and `Clip` had scalar `Compile[]` lowerings but declined an array
operand, so `Compile[{{v, _Real, 1}}, Chop[v]]` / `Clip[v, {lo, hi}]` fell back
to the interpreter — and because the compilable subset is a cliff, dragged any
enclosing body down with them. They now lower over a **rank-1 array** by reusing
the scalar lowering per element: the array branch synthesises
`Map[Function[H[#, rest...]], arr]` and delegates to the existing Map
elementwise loop, so the array answer is the scalar one applied elementwise,
**bit for bit**, and every argument form (Chop's `delta`, Clip's `{lo, hi}`)
rides the scalar arm with no new opcodes. Auto-compilation follows for free;
rank-2+ declines gracefully to the interpreter.

  declared in `compile_internal.h`); `infer_elem_over_array` /
  `emit_map_over_array` wrappers and rank-1-array branches in the `Chop`,
  `Clip`(1) and `Clip`/`Rescale`(2) arms of `compile_infer.c` /
  `compile_emit_mathfn.c`.

## Integrate: a parameter spelled C[2] / c[2] no longer zeroes the log part ; v0.359

`Integrate[1/(c[2] - u^2), u]` returned **0**, and `Integrate[1/Sqrt[C[2] - 2a/w], w]`
lost its ArcTanh term (the same integrals over a plain symbol `k` were right). Two
bugs:

- `intsimp_sign_pos_assumption` treats free *symbols* as positive but gave an
  undefined-head application such as `c[2]` sign 0. The discriminant `16 c[2]`
  therefore read as sign-unknown, sending `logtoreal_quadratic` to its complex-pair
  branch.
- That branch's `intsimp_pos_sqrt(-16 c[2])` produced `4 I Sqrt[c[2]]`, which made
  the ArcTan argument imaginary and collapsed the contribution to 0. The same
  collapse hit any sign-undecided monomial, e.g. `Integrate[1/(Sin[k] - u^2), u]`
  was 0.

An undefined-head application now counts as a positive parameter like a symbol, and
an imaginary `Sqrt[-disc]` is held as `Sqrt[-disc]`. The `IntegrateRationalTests`
and inline rational cases are byte-identical.


## RealDigits: correct exponent and digits at powers of the base ; v0.358

**Bug fix (correctness).** `RealDigits[x]` for an inexact `x` returned a wrong
second element (the exponent) — and, for an exact power of the base, wrong
digits — whenever `x` sat at or just below a power of the base. The digit list
was placed from the full-precision canonical exponent (`mpfr_get_str` at the
available precision), but the reported exponent and `start_pos` came from two
*different*, carelessly-rounded estimates, so the two disagreed exactly at the
boundary:

- `RealDigits[0.9991251116426123]` → exponent `1` (should be `0`); likewise
  `0.999`, `0.9999999999`, `99.6` (gave `3`), `0.0999999999999999` (gave `0`).
  Cause: a fix-up that re-derived the exponent with a **2-significant-digit,
  round-to-nearest** `mpfr_get_str` — a `99…` tail rounds up to `10…` and carries
  the exponent a whole decade.
- `RealDigits[1000.]` → `{{0,0,…,Indeterminate}, 4}` (should be
  `{{1,0,0,0,…}, 4}`); same for `N[10^15]`. Cause: `rd_inexact_natural_exp`
  used `floor(log(x)/log(b)) + 1`, and `log(1000.)/log(10.) = 2.9999999996`
  floors to 2, so `start_pos` was one short and the leading digit fell off the
  front of the window.
- Large magnitude: `RealDigits[N[9959306433341448*10^240]]` → exponent `257`
  (should be `256`) — the same `99…`-carry.

**Fix (`src/real.c`).** `rd_inexact_natural_exp` now reads the exponent from
`mpfr_get_str` at the *same* digit count (`rd_available_digits`) and rounding
(`RNDN`) that `rd_inexact_canonical_digits` uses to lay the digits out, so the
reported exponent and the digit placement are the one same quantity and cannot
disagree. A carry there (a value that rounds up to a power of the base at full
precision) is self-consistent: the digits become `10…` and the exponent moves
with them. The old 2-digit boundary fix-up is removed. The no-`MPFR` build keeps
the `log`-quotient estimate. Controls unchanged: `123.55555` → `{…, 3}`,
`0.89`/`0.95`/`0.1` → `{…, 0}`, `1.0` → `{…, 1}`, `N[Pi, 50]` → `{…, 1}`,
negatives and the inexact-zero convention untouched. New regression cases in
`tests/test_real_digits.c` (`test_real_near_one_exponent`,
`test_real_boundary_exponents`, `test_real_power_of_ten_digits`); full suite
green; valgrind-clean (no new leaks). Found while stress-testing `ChebyshevT`
(the harness's digit emitter tripped over it).

## ChebyshevT: real-only MPFR recurrence branch (arbitrary-precision real speedup) ; v0.357

**A cross-system stress test of `ChebyshevT` confirmed it correct and highly
efficient in every numeric regime, and exposed one clean arbitrary-precision
perf win, now closed.** The test ran 50 argument probes across machine
real/complex and arbitrary-precision real/complex — integer/negative/non-integer
and complex order, cancellation, branch-cut edges, and special values — against
SciPy `eval_chebyt`, SymPy `chebyshevt`, mpmath `chebyt` and wolframscript
(Wolfram Engine 14.0), scored against a 260-digit mpmath oracle.

- **Correctness: 0 disagreements.** Every class-A probe matched the oracle in all
  four regimes (one fully-exact complex-order call stays symbolic by design).
  Mathilda is *more* accurate than Wolfram on the hard machine-complex cases
  (`ChebyshevT[1000, 0.3 + 0.1 I]`: ~6 ULP vs WL ~2180 ULP; exact `0` at
  `T_49(0)` where WL carries ~8e-15 roundoff) and far more accurate than SciPy,
  whose complex `eval_chebyt` is wildly inaccurate (10²¹–10²⁸ ULP off) for
  arguments away from `[-1, 1]` — not a Mathilda issue, but it rules SciPy out as
  an oracle for the complex regimes.
- **Cross-surface bit-identity.** Scalar == unpacked List == packed List ==
  `NDArray` == `Compile[]` to the last bit, for machine real and complex argument
  at integer orders straddling the fast-path edge (n = 50, 1000, 1001); all four
  `Compile[]` shapes report `Compiled -> True`.
- **Efficiency.** Machine real ~11 ns/element (≈5× NumPy's `eval_chebyt`, ≈228×
  wolframscript); machine complex ~20 ns/element (≈25× NumPy). Arbitrary
  precision was within ~2.3–2.4× of mpmath — both on GMP/MPFR, so core-vs-core
  (wolframscript wins the arb-prec scalar via an `O(1)` closed form; matching that
  is a documented follow-up, not a kernel gap).

**The fix (`src/special_functions/chebyshev_t.c`, `cheb_numeric_recurrence`).**
The arbitrary-precision three-term recurrence always ran in complex `ncpx`
arithmetic, even for a purely real argument — paying for an always-zero imaginary
part on every one of the `n` steps (two real multiplies and a handful of
real add/sub per complex multiply that do nothing). The recurrence now branches
on `mpfr_zero_p(x.im)`: a real argument runs a plain `mpfr_t` recurrence (`r_k =
2 x r_{k-1} - r_{k-2}`), and only a genuinely complex argument takes the `ncpx`
path, which is **byte-for-byte unchanged**. **A/B-measured ~7–8% faster** on real
arbitrary-precision evaluations (`ChebyshevT[1000, 1/3]` at 200 digits: 1873 →
1722 ms over 100 distinct inputs; `ChebyshevT[2000, ·]` at 300 digits: 3580 →
3333 ms), with the complex regime and all machine regimes untouched. Accuracy is
identical (the real and complex recurrences compute the same real value; the
complex path merely carried a zero imaginary part through). No new builtins,
attributes, or API; no `pack.c` / `compile_*` / ND-kernel edits (the change is
below the machine fast path). `chebyshev_t_tests` green, `check-nd-surfaces`,
`check-compile-coverage`, `check-array-exactness`, `check-packed-aware`,
`check-c99`, `check-messages` pass, valgrind reports no new leaks.
