# Changelog: week of 2026-10-12 (Mon) – 2026-10-18 (Sun)

## Parser: empty argument / element slots are Null ; v0.408

Mathematica reads an omitted element next to a comma as `Null`. Mathilda used to
drop a leading comma silently (`f[,x]` parsed as `f[x]`, `{,1}` as `{1}`) and
rejected trailing and doubled commas as syntax errors.

| Input | Before | Now (= Mathematica) |
|---|---|---|
| `f[,x]` | `f[x]` | `f[Null, x]` |
| `f[x,]` | syntax error | `f[x, Null]` |
| `f[x,,y]` | syntax error | `f[x, Null, y]` |
| `{,1}` / `{1,}` | `{1}` / syntax error | `{Null, 1}` / `{1, Null}` |
| `f[]`, `{}` | empty | empty (unchanged) |

- **`src/parse.c`**: the duplicated argument loops of `parse_list` and
  `parse_function` are replaced by one `parse_sequence(s, close, what, &n)`,
  which implements the rule: an empty pair has no elements, and every slot
  around a comma is an element, `Null` when nothing is written. A missing
  closer (`f[x y`, `{1, 2`) is still a syntax error, now reported once at the
  level where it is missing instead of once per enclosing bracket.
- Regression test: `test_parse_empty_slots_are_null` (`tests/test_parse.c`).

## Parser: a bare `[` is a syntax error, not a NULL-head call (segfault fix) ; v0.407

`f[x,[x]]` and `Solve[x,[x]]` (issue #89) segfaulted. `parse_primary` treated a
`[` that has nothing in front of it as an "anonymous function" and built an
`EXPR_FUNCTION` with a **NULL head**. It survived parsing (`FullForm` printed it as
`Null[x]`), and the evaluator crashed reading `head->type` in `evaluate_step`. No
other code builds a NULL-head node.

- **`src/parse.c` `parse_primary`**: a leading `[` is now a parse failure, so the
  input gets the usual `syntax error` report (REPL: `Parse error`; `-file`: exit
  1), as in Mathematica. `g[[x]]` (Part) and `f[x][y]` are postfix on a real head
  and are unaffected.
- **`;` followed by `[`** (`a; [y]`): an implicit trailing `Null` is no longer
  inserted when the next token is `[`. Before this, the `[y]` was silently parsed
  as a call on `CompoundExpression[a, Null]`. Now it is a syntax error. Trailing
  `a;`, `f[a;]` and `(a;)` still give `CompoundExpression[a, Null]`.
- **Leak**: `parse_function` now frees its `head` on both failure paths. Its only
  caller drops the head when the call returns NULL, so every function-call syntax
  error (`f[x,]`, `f[x, (]`, …) used to leak the head. Valgrind on the error path
  now matches the clean-run startup baseline.
- Regression test: `test_parse_headless_bracket` (`tests/test_parse.c`).

## Native Windows (MSYS2/MinGW UCRT64) clean compile + CI gate ; v0.406

Mathilda is packaged for native Windows via MSYS2/MinGW (passagemath PR #2966),
and v0.387 stopped building there because the `TimeConstrained` async-timeout
engine and `getrusage` memory stats landed using POSIX symbols MinGW lacks (no
Cygwin layer). Mathilda was already largely Windows-hardened (the makefile forces
`USE_READLINE=0`/`USE_THREADS=0` on Windows; `repl.c`/`loadmodule.c`/`files.c`/
`label_font.c` carry `_WIN32` paths; no `dlopen`/`fork`/`popen`), so this is a
regression fix, not a port. The genuinely unguarded blockers are now closed, and
a CI leg keeps them closed.

- **New `src/mtime.{c,h}` timing shim** — `mth_mono_seconds` / `mth_wall_seconds`
  / `mth_sleep_seconds`, the single OS seam for clocks and sleep
  (`clock_gettime`/`nanosleep` on POSIX; `QueryPerformanceCounter` /
  `GetSystemTimePreciseAsFileTime` / `Sleep` on Windows). Replaces **five**
  copy-pasted `clock_gettime(CLOCK_MONOTONIC)` helpers (`core.c`, `datetime.c`,
  `simp/simp_util.c`, `calculus/integrate.c`, `calculus/integrate_derivdivides.c`),
  which now delegate to it — behaviourally identical on macOS/Linux.
- **`TimeConstrained` (`src/core.c`)** — the SIGPROF/`setitimer`/`sigaction`
  async-preemption layer is now `#ifndef _WIN32`; a portable `TC_SETJMP`/
  `TC_LONGJMP` macro selects `sigsetjmp`/`siglongjmp` on POSIX and plain
  `setjmp`/`longjmp` on Windows; the cooperative wall-clock deadline moved to a
  `double` driven by `mth_mono_seconds`. On Windows `TimeConstrained` is
  therefore **cooperative-only** (the existing WSL-1 path): it enforces the
  budget through the evaluator loop and the `tc_deadline_passed()` kernel polls,
  but cannot forcibly interrupt a C builtin that never checks in. POSIX behaviour
  is unchanged (verified: abort, failexpr, nesting, Infinity).
- **`src/meminfo.c`** — `getrusage`/`<sys/resource.h>` guarded; `MemoryInUse[]`
  and `MaxMemoryUsed[]` get a `GetProcessMemoryInfo` branch on Windows (link
  `-lpsapi`). **`src/files.c`** — `FileExistsQ`'s `lstat` aliases to `stat` on
  Windows (no POSIX symlink notion there). **`src/ffi/mathilda_ffi.c`** —
  `setenv` → `_putenv` on Windows.
- **Build/docs** — makefile adds `-lpsapi` on Windows and documents that MPFR
  (default-ON, no degrade) must be installed or disabled; `TARGET` is
  `Mathilda.exe` on Windows so the link rule's timestamp is honest.
  `docs/building.md` lists `mingw-w64-x86_64-mpfr` and the Windows degradations;
  `SPEC.md §10` gains the native-Windows portability contract.
- **Gates** — `tools/check_c99_portability.py` gains a MinGW-missing-symbol scan
  (`setitimer`/`getrusage`/`lstat`/`setenv`/the `sigaction`/`sigsetjmp` layer,
  …): a use not guarded by `_WIN32` (or aliased under it) fails `make check-c99`,
  assert-empty today. `.github/workflows/build.yml` gains a real **MSYS2/UCRT64**
  build+smoke job (the authoritative gate; the smoke test exercises the
  cooperative-only `TimeConstrained` and the `GetProcessMemoryInfo` path).
- macOS build clean; `make check-c99` (incl. the new scan) passes; behaviour of
  `TimeConstrained`/`AbsoluteTiming`/`Timing`/`MemoryInUse`/`MaxMemoryUsed`/
  `FileExistsQ`/`Pause`/`SessionTime`/`DateList` all verified unchanged.

## Definite integration of the parameter / Frullani-log family ; v0.405

New definite-integration stage `Integrate\`FeynmanParameter`
(`src/calculus/integrate_feynparam.c`) — differentiation under the integral sign
w.r.t. a present parameter, specialised to the family that makes the trick close in
one step:
`Integrate[(Sum_i c_i x^(e_i))/Log[x], {x,0,1}] = Sum_i c_i Log[e_i + 1]`, valid when
`Sum_i c_i = 0` (so the `1/Log[x]` singularity at `x=1` is integrable) and each
`e_i + 1 > 0`. Closes the archetype `Integrate[(x^a-1)/Log[x], {x,0,1}] = Log[a+1]`
(`a > -1`) — the MSE *tough integrals* thread's parameter-differentiation example —
and generalises it: `(x^a-x^b)/Log[x] → Log[(a+1)/(b+1)]`,
`(x^3-x^(1/2))/Log[x] → Log[8/3]`, `(2x^4-x-1)/Log[x] → Log[25/2]`.

- The inner `x`-power integral is taken **directly** as `1/(e+1)` rather than via
  `Integrate`, which sidesteps the current `Beta[1+a,1]` / `Gamma[1+a]/Gamma[2+a]`
  form the simplifier does not reduce to `1/(1+a)` (so the integrate-back closes),
  and keeps the stage cheap — it does no long re-entrant `Integrate` and stays clear
  of the slow parametric cascade. Each `e_i + 1 > 0` is proved from Assumptions, and
  the closed form is numerically cross-checked against `NIntegrate` at an in-domain
  parameter sample before returning; it declines otherwise (`Sum c_i != 0`, a
  non-power term, an unprovable domain, or a failed check). `Integrate[1/Log[x],
  {x,0,1}]` (sum of coefficients `!= 0`, divergent) is correctly left unevaluated.
- Reachable as `Method -> "FeynmanParameter"`; runs in the pre-FTC `[0,1]` block
  (these integrands have no elementary antiderivative). Symbolic-result stage, so
  packed/NDArray and `Compile[]` do not apply.
- Completes the MSE "simple techniques" campaign: the dedicated corpus
  `tests/MseTrickIntegralsCorpus.m` is now 15/15 CORRECT, 0 WRONG. See
  `tasks/mse_trick_integrals_2026-10-14.md`.

## Definite integration by general King reflection ; v0.404

New definite-integration stage `Integrate\`King` (`src/calculus/integrate_king.c`),
the general **King reflection** `x -> a+b-x`: for a finite interval
`Integrate[f,{x,a,b}] = (1/2) Integrate[f(x)+f(a+b-x),{x,a,b}]`, and when the
reflected sum `f(x)+f(a+b-x)` is a **constant** `c` the value is `c (b-a)/2`. This
closes the classic trick integral with no elementary antiderivative
`Integrate[1/(1+Tan[x]^Sqrt[2]), {x,0,Pi/2}] = Pi/4` (and the whole
`1/(1+Tan[x]^s)` / `1/(1+Cot[x]^s)` family for any real `s`, integer or
irrational).

- The constancy of `f(x)+f(a+b-x)` cannot be proved symbolically — Simplify does
  not know `(Tan·Cot)^s = 1` — so the constant is read at the interval **midpoint**
  (`Simplify[h /. x->(a+b)/2]`), screened numerically across several interior
  points, and the final value is **cross-checked against `NIntegrate`**. A
  mis-detected constancy produces `c(b-a)/2 != ∫f`, which the check rejects, so the
  stage never returns a wrong answer; it declines (returns the input unevaluated)
  otherwise.
- **Numeric-domain precondition** (correctness + robustness): King is an inherently
  numeric method, so it fires only on a parameter-free integrand (one that
  evaluates to a number at a numeric `x`), screened cheaply up front before any
  reflection/Simplify work. A parametric integrand such as `(x^a-1)/Log[x]` is out
  of scope and declined immediately.
- Complements the existing `integrate_kingreflect_try` (the distinct `x·g(x)`,
  `g` invariant shape). Reachable as `Method -> "King"` / `"Reflection"`; runs
  before Newton–Leibniz so these no-elementary-antiderivative integrands close
  without a spurious `Integrate::nonelem`.
- Symbolic-result stage (returns closed-form constants), so the packed/NDArray and
  `Compile[]` surfaces do not apply. No new leaks (identical fixed startup
  baseline); valgrind shows no invalid access; check-c99 / check-messages pass.
- Corpus `tests/MseTrickIntegralsCorpus.m` + gate `mse_trick_corpus_tests`
  (`tests/test_mse_trick_corpus.c`).

## Definite integration by series expand → term-by-term → resum ; v0.404

New definite-integration stage `Integrate\`SeriesExpansion`
(`src/calculus/integrate_series.c`) — the **alternating sibling** of
`integrate_ratlog01_try`. It closes log-weighted rational integrals on `[0,1]`
with a root-of-unity denominator `1 ± x^d` whose antiderivative is a non-elementary
PolyLog, by expanding the geometric series, integrating term-by-term with the exact
identity `Integrate[x^m Log[x]^k, {x,0,1}] = (-1)^k k!/(m+1)^(k+1)`, and resumming
each residue class with the existing `Sum[]` engine (→ `Catalan`, `DirichletBeta`,
`Zeta`). New results include:

- `Integrate[Log[x]/(1+x^2), {x,0,1}] = -Catalan`
- `Integrate[Log[x]^2/(1+x^2), {x,0,1}] = Pi^3/16`
- `Integrate[Log[x]/(1+x), {x,0,1}] = -Pi^2/12`, `…^2/(1+x) = (3/2)Zeta[3]`,
  `…^3/(1+x) = -7 Pi^4/120`
- `Integrate[x^2 Log[x]/(1+x^2), {x,0,1}] = Catalan - 1` (polynomial-division path)
- general cyclotomic denominators, e.g. `Log[x]/(1+x^3)`, `Log[x]^2/(1+x^2+x^4)`.

- **Correct by construction**: the general coefficient comes from exact cyclotomic
  divisibility (`PolynomialRemainder[1 ∓ x^d, Q, x] == 0`) and the geometric-series
  identity — never inferred from samples — and the `Log[x]^k` weight (`k >= 1`)
  forces the resummed p-series to converge absolutely (`p = k+1 >= 2`). The value is
  additionally **cross-checked against `NIntegrate`**; it declines on any
  non-rational factor, non-`[0,1]` interval, pole at `x=0`, non-cyclotomic
  denominator, or unclosed resummation. The `1 - x^m` HurwitzZeta family stays
  owned by `integrate_ratlog01_try` (runs first); the alternating `1 + x^d` case it
  cannot represent is this stage's.
- Reachable as `Method -> "SeriesExpansion"` / `"SeriesTermByTerm"`; runs in the
  pre-FTC `[0,1]` block so these PolyLog-antiderivative integrands close without a
  spurious `Integrate::nonelem`.
- Symbolic-result stage, so packed/NDArray and `Compile[]` do not apply. No new
  leaks; check-c99 / check-messages pass; the three existing definite-integral
  corpora (extreme, singular, intrat) stay green.

These extend the definite-integration suite toward the "simple techniques" of the
MSE *tough integrals* thread; see `tasks/mse_trick_integrals_2026-10-14.md`.

## Complex arrays auto-pack (RandomComplex + complex Lists) ; v0.402

Machine **complex** arrays now pack into a `complex64` buffer, so the whole
NDArray/packed fast path — element-wise kernels (`Sin`, `Exp`, `HermiteH`, …),
`Compile[]`, reductions — runs on the buffer instead of threading boxed
`Complex[…]` leaves one at a time. Previously only real/integer/boolean lists
packed; a complex list fell to the element-wise interpreter path, ~150× slower
than the kernel it already had. Surfaced by the HermiteH efficiency review:
`HermiteH[20, RandomComplex[…, 10^6]]` went **1.29 s → 0.017 s (74×)**, `Sin` on
the same data **2.68 s → 0.015 s (175×)**; a packed complex buffer now runs
HermiteH at ~115 M elem/s, ~25× NumPy's vectorised recurrence and ~1000× Wolfram.

- **`src/pack.c`** — the packing substrate learns a `PK_COMPLEX` leaf class: a
  `Complex[re, im]` with two machine-`Real` components packs to `NDT_COMPLEX64`
  (`leaf_class`, `pack_fold_class`, `pack_sniff`, `pack_build`, `pack_flatten`;
  an explicit `DataType -> "complex64"` may now widen a numeric list). Lossless
  with **no materialisation fold**: the evaluator folds `Complex[x, 0.] -> Real`
  before any list is built, so an all-`Complex` list has no `im == 0` element to
  misrepresent as `Complex[re, 0]` on the way back — and a mixed `{Complex, Real}`
  list is heterogeneous, so (as in Wolfram) it does not auto-pack. Exact Gaussian
  integers (`Complex[1, 2]`) still decline: widening their parts to doubles would
  be the same `exact -> inexact` head change auto-packing never makes.
- **`src/random.c`** — `RandomComplex[range, n]` and `RandomComplex[range,
  {…}]` fill a `complex64` buffer directly (mirroring how `RandomReal` fills
  `float64`), at the same re-then-im draw order so a seeded stream is unchanged; a
  degenerate zero-imaginary range keeps the old Real-valued List path.
- Audits green (array-exactness, nd-surfaces, compile-coverage); no new leak
  (identical fixed startup baseline); check-c99 / check-messages pass; the focused
  complex/ndarray/packed/random/linalg suite A/B shows an identical pre-existing
  FAIL set (no regression). Known follow-up: a `Table`/`Sum` body that builds a
  complex list element-by-element is still boxed (complex auto-compilation of the
  loop body is separate); the resulting array packs and downstream ops are fast.

## HermiteH: physicists' Hermite polynomials ; v0.401

New builtin `HermiteH[n, x]` (`src/special_functions/hermite_h.{c,h}`), modelled
on ChebyshevU and reusing the family-agnostic `chebyshev_common.{c,h}` substrate
(no change to ChebyshevT/U). `Listable, NumericFunction, Protected`.

- **Exact polynomial** for a non-negative integer order via FLINT
  `fmpz_poly_hermite_h` (or the integer three-term recurrence `H_0=1`, `H_1=2x`,
  `H_k = 2x H_{k-1} - 2(k-1) H_{k-2}`): `HermiteH[10,x]`, `HermiteH[7,x]`,
  `Table[HermiteH[10,x],{x,1,5}] = {8224, 200416, -3093984, 125984224,
  3275529760}`.
- **Numerics** at machine and MPFR precision, real and complex, in both the
  order and the argument. An integer order with an inexact argument uses the
  *stable* recurrence (not polynomial substitution), so `HermiteH[100, N[5,16]] =
  8.19…×10^98` where the expanded polynomial cancels to garbage. A non-integer /
  complex / negative order uses the entire confluent-hypergeometric form
  `2^n Sqrt[Pi](1F1[-n/2,1/2,x^2]/Gamma[(1-n)/2] - 2x 1F1[(1-n)/2,3/2,x^2]/
  Gamma[-n/2])`, evaluated with a cancellation guard scaled to `Re(x^2)` so a
  large real argument keeps its digits (`HermiteH[3.-4.583I,5] = -731.082 +
  940.003 I`). Special value `HermiteH[n,0] = 2^n Sqrt[Pi]/Gamma[(1-n)/2]`.
- **Fast paths.** Machine `double`/`double`-complex helpers
  `sf_machine_hermite_h[_c]` (`src/special_functions/sf_machine.c`) shared
  bit-for-bit by the scalar path, the NDArray binary kernel `ndk_HermiteH_c`
  (`src/ndkernels.c`, with a complex arm, auto-`packed_aware` via `REG_B`), and
  `Compile[]` / auto-compilation (generic over the registered kernel — scalar and
  rank-1 array both `Compiled -> True`). No `pack.c`/`compile/` edits needed.
- **Derivative** `D[HermiteH[n,z],z] = 2 n HermiteH[n-1,z]`
  (`src/calculus/deriv.c`), which also powers `Interval[]` threading and, via
  Taylor-via-D, the finite-point `Series` for free (`Series[HermiteH[n,x],{x,x0,
  2}]`, `Series[HermiteH[1/2,x],{x,0,3}]`).
- **Series at Infinity** (bespoke, `try_series_hermiteh_at_infinity` in
  `src/calculus/series.c`): the algebraic `(2x)^n 2F0(-n/2,(1-n)/2;;-1/x^2)`
  asymptotics, symbolic order (the subdominant `e^(x^2)` branch is not included).
  **SeriesCoefficient** symbolic index at `x0=0` as a parity `Piecewise`
  (verified to ~1e-49 against the concrete path across a non-integer grid).
- Symbol interned in `sym_names.{c,h}`; docstring in `info.c`; registered in
  `core_init`. Unit suite `tests/test_hermite_h.c` (polynomials, values,
  Listable, machine/MPFR/complex numerics, cancellation, derivative, Series,
  SeriesCoefficient, argcount, attributes) passes; docs in
  `docs/spec/builtins/special-functions.md`. check-c99 / check-messages pass; no
  leak.

## Integrate: Gaussian-moment difference on [0, Infinity) ; v0.398

`gaussdiff_try` (`src/calculus/integrate_ramanujan.c`): the Mellin-moment
combination `Integrate[x^k Sum_i C_i Exp[-p_i x^2], {x,0,Inf}] = (1/2) Gamma[s/2]
Sum_i C_i p_i^(-s/2)`, `s = k+1`, `p_i > 0` (the analytically-continued Mellin
transform `M[Exp[-p x^2]](s) = (1/2) p^(-s/2) Gamma[s/2]`).  A single Gaussian
moment with `s <= 0` diverges at 0; a difference like
`(Exp[-a x^2] - Exp[-b x^2])/x^2` converges because the lower-power coefficients
cancel.  Soundness gate: every divergent-at-0 coefficient `Sum_i C_i p_i^m`
(`m = 0 .. floor((-1-k)/2)`) must vanish, `Gamma[s/2]` must be finite (`s` not a
non-positive even integer), and each `p_i` is proved `> 0` — so the divergent
single Gaussian and a non-Gaussian `(Exp[-a x]-Exp[-b x])/x^2` both decline.  A
whole-integrand pre-pass (alongside Frullani) in the Ramanujan/Mellin stage.
Closes extreme battery #2 case 6 `(Exp[-a x^2]-Exp[-b x^2])/x^2 = Sqrt[Pi]
(Sqrt[b]-Sqrt[a])` (45 → 46 of 50, 0 wrong).  Ramanujan / integrals /
diffunderint suites green; battery #1 unchanged (44); check-c99 / check-messages
pass; no leak.

## LegendreP / LegendreQ: associated forms evaluate by Horner over arrays ; v0.376

Stress-testing the associated `LegendreP[n, m, x]` (and the type-2/3
`LegendreP[n, m, a, x]`) against SciPy's `lpmv` over machine arrays found a
high-degree performance pathology.

- **The gap.** These forms build the explicit degree-`n` polynomial and evaluate
  it over the buffer as a sum of monomials `Σ cₖ xᵏ` -- each `xᵏ` its own
  full-buffer `pow()`. So the cost was `O(n)` `pow()` passes and grew
  pathological with `n`: `LegendreP[30, 4, array]` over 10⁶ points did not finish
  in ~85 s (SciPy's `lpmv`: 20 ms). Low degree was already correct, packed, and
  ahead of SciPy -- only high degree suffered.
- **The fix.** For a packed-List / `NDArray` machine argument the polynomial is
  now evaluated by **Horner in machine `double`** (`leg_poly_from_coeffs`, plus
  `legendre_2f1reg_core` for types 2/3) -- `O(n)` fused multiply-adds, no
  `pow()`. The Plus/Times buffer fast paths take a Real scalar but not a
  Rational, so the coefficients are coerced to `double` (exactly what the buffer
  arithmetic did anyway), keeping the answer unchanged to rounding (~1e-13
  vs the scalar path). The Horner route fires **only** for a numeric buffer, so
  the symbolic output of every form -- `LegendreP[5, x]`, `LegendreP[5, 3, x]`,
  the type-2/3 branch forms -- is byte-identical. `LegendreQ`'s associated form
  shares `leg_poly_from_coeffs` and is fixed with it.
- **Result (10⁵ points).** `LegendreP[12, 3, x]` 14.8 ms → 6.7 ms;
  `LegendreP[30, 4, x]` >85 s → 10.6 ms; `LegendreP[50, 3, x]` → 20.5 ms. The
  three-argument form is now faster than SciPy's `lpmv` at every degree tested
  (≈1.4–1.9×); it was already correct (matches `lpmv`), packed, and
  cross-surface consistent. A grid of `(n, m, x)` points (real/complex,
  types 1/2/3) is unchanged against the scalar path to ~1e-12.

Touched: `src/special_functions/legendre.c`, `src/version.h`. Spec:
`docs/spec/builtins/special-functions.md`.

## LaguerreL: generalized three-argument form threads over arrays ; v0.375

Stress-testing `LaguerreL` against SciPy (`eval_laguerre` / `eval_genlaguerre`)
and Mathematica over machine arrays exposed a performance and consistency gap in
the **generalized three-argument** form `LaguerreL[n, a, x]` over a packed-List
or visible `NDArray` argument.

- **The gap.** The two-argument form reaches a binary ND kernel at the REPL
  element-wise fast path, but a three-argument call has no arity-≥3 element-wise
  path there (the N-ary kernel is read only by `Compile[]`). So `LaguerreL[n, a,
  NDArray]` fell through to the builtin and re-expanded the explicit degree-`n`
  polynomial over the buffer — correct, but ~20–40× slower than the scalar
  machine recurrence and **not bit-identical** to it (the array path differed
  from the scalar/List/`Compile[]` answer by ~1e-12).
- **The fix.** `builtin_laguerre_l` now threads the *same* machine helper
  `sf_machine_laguerre_l_assoc[_c]` element-wise over a real or complex buffer
  (`src/special_functions/laguerre_l.c`), holding the integer order and machine
  parameter constant and returning a buffer that inherits the argument's
  presentation (packed List ↔ visible `NDArray`). Because it reuses the scalar
  path's helper, `scalar == List == packed == NDArray == Compile[]` is now
  bit-identical for the three-argument form too. An `"int64"` buffer, a
  non-machine parameter, order `n > 1000`, or an overflowing element declines
  and delists to the exact / MPFR route unchanged.
- **Result (1e6 points).** `LaguerreL[12, 2.5, x]` over a packed array: 148 ms →
  39 ms. `LaguerreL[50, 2.5, x]`: previously exhausted memory, now 222 ms. The
  three-argument form is now faster than SciPy for degrees up to ~12 (≈1.75×),
  at parity at degree 50, and ~50–500× faster than Mathematica (which does not
  vectorise `LaguerreL` over a packed array). The two-argument form was already
  ~4.7× faster than SciPy and is unchanged. A full grid of 900+ `(n, a, x)`
  points (real/complex, integer/non-integer/negative order, orders to 300)
  matches mpmath to < 4.1e-14.

Touched: `src/special_functions/laguerre_l.c`, `src/version.h`. Spec:
`docs/spec/builtins/special-functions.md`.

## LaguerreL: Laguerre and generalized Laguerre polynomials ; v0.374

New builtin `LaguerreL[n, x]` (Laguerre polynomial `L_n(x)`) and `LaguerreL[n,
a, x]` (generalized `L_n^(a)(x)`, with `LaguerreL[n, x] == LaguerreL[n, 0, x]`),
to the ChebyshevU bar — symbolic, numeric, packed/NDArray, and `Compile[]`.

- **Exact polynomial.** A non-negative integer order yields the explicit
  polynomial: exact rational coefficients via the three-term recurrence for a
  numeric/absent parameter `a`, and the expanded polynomial in `a` and `x` for a
  symbolic `a`. `LaguerreL[5, x] = 1 - 5 x + 5 x² - 5/3 x³ + 5/24 x⁴ - 1/120 x⁵`,
  `LaguerreL[2, a, x] = 1 + 3/2 a + 1/2 a² - 2 x - a x + 1/2 x²`,
  `Table[LaguerreL[10, x], {x, 1, 5}] = {168919/403200, -4381/14175,
  -31361/44800, 931/675, 254927/145152}`.
- **Numerics.** Integer order with an inexact argument uses the *stable*
  recurrence rather than polynomial substitution, so `LaguerreL[100, 0, N[5,
  20]] = 1.4555271625328812607` instead of the catastrophically-cancelled
  `1.4557…`. Non-integer / complex order evaluates through the entire form
  `Binomial[n+a, n] Hypergeometric1F1[-n, a+1, x]` — machine or MPFR, real or
  complex: `LaguerreL[6., 5] = -2.09028`, `LaguerreL[6. - I, 5] = -2.76039 -
  2.46853 I`, `LaguerreL[2.5, 1.3, 8 + I] = 8.50391 + 0.576867 I`,
  `N[LaguerreL[2/5, 1/3, 8/7], 50]` to 50 digits.
- **Special values.** `LaguerreL[0, x] = 1`, `LaguerreL[n, 0] = Binomial[n+a,
  n]` (= 1 for the ordinary polynomial).
- **Derivative.** `D[LaguerreL[n, x], x] = -LaguerreL[n-1, 1, x]`;
  `D[LaguerreL[n, a, x], x] = -LaguerreL[n-1, a+1, x]`.
- **Fast paths.** A binary ND kernel (`sf_machine_laguerre_l[_c]`) gives the
  two-argument form NDArray + packed + `Compile[]` + auto-compilation, with a
  machine-complex arm; the scalar machine path dispatches to the same helper, so
  scalar == List == packed == NDArray == `Compile[]` bit-for-bit. The generalized
  three-argument form adds an N-ary kernel for scalar `Compile[]`.
- **Attributes.** `Listable`, `NumericFunction`, `Protected`. Diagnostics route
  through `mth_message` (`LaguerreL::argt`).

## Series: assumption-aware branch selection — 7 gaps closed ; v0.368

## RealDigits: correct exponent and digits at powers of the base ; v0.358

**Bug fix (correctness).** `RealDigits[x]` for an inexact `x` returned a wrong
second element (the exponent) — and, for an exact power of the base, wrong
digits — whenever `x` sat at or just below a power of the base. The digit list
was placed from the full-precision canonical exponent (`mpfr_get_str` at the
available precision), but the reported exponent and `start_pos` came from two
*different*, carelessly-rounded estimates, so the two disagreed exactly at the
boundary:

- `RealDigits[0.9991251116426123]` → exponent `1` (should be `0`); likewise
  `0.999`, `0.9999999999`, `99.6` (gave `3`), `0.0999999999999999` (gave `0`).

  round-to-nearest** `mpfr_get_str` — a `99…` tail rounds up to `10…` and carries
  the exponent a whole decade.
- `RealDigits[1000.]` → `{{0,0,…,Indeterminate}, 4}` (should be

  front of the window.
- Large magnitude: `RealDigits[N[9959306433341448*10^240]]` → exponent `257`
  (should be `256`) — the same `99…`-carry.

reported exponent and the digit placement are the one same quantity and cannot
disagree. A carry there (a value that rounds up to a power of the base at full
precision) is self-consistent: the digits become `10…` and the exponent moves
with them. The old 2-digit boundary fix-up is removed. The no-`MPFR` build keeps
the `log`-quotient estimate. Controls unchanged: `123.55555` → `{…, 3}`,

green; valgrind-clean (no new leaks). Found while stress-testing `ChebyshevT`

## ChebyshevT: real-only MPFR recurrence branch (arbitrary-precision real speedup) ; v0.357

**A cross-system stress test of `ChebyshevT` confirmed it correct and highly
efficient in every numeric regime, and exposed one clean arbitrary-precision
perf win, now closed.** The test ran 50 argument probes across machine
real/complex and arbitrary-precision real/complex — integer/negative/non-integer
and complex order, cancellation, branch-cut edges, and special values — against
SciPy `eval_chebyt`, SymPy `chebyshevt`, mpmath `chebyt` and wolframscript
