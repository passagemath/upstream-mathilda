# Changelog: week of 2026-10-26 (Mon) – 2026-11-01 (Sun)

## A declining call reports its message once ; v0.6024

When the pack gate unpacks a packed argument and a non-`Listable` head still
declines the call with a message, the call now settles. Before, the unpacked
form was evaluated again on the next step and the message printed twice:
`za = Range[6]; Dot[za, {1, 2}]` reported `Dot::dotsh` twice. A `Listable` head still takes the extra step,
because its unpacked call threads over the list. A settled step that contains a
pack-gate materialisation now keeps the newer, unpacked representation.
`tests/test_eval_timestamps.c` (`test_declining_call_reports_once`) counts the
messages fired for `Det` and `Dot` declines, both bare and as assignment values.

## Build: the `USE_MPFR=0` configuration compiles again

`src/special_functions/stieltjesgamma.c` and `src/special_functions/surd.c`
used `EXPR_MPFR` and `numeric_min_inexact_bits` unguarded. Both exist only under
`USE_MPFR` (the uses date from v0.477), so the `build-no-mpfr` CI job failed on every push. The
uses are now fenced by `#ifdef USE_MPFR`; the default build is unchanged. The
whole tree compiles and links with `make USE_MPFR=0 USE_FLINT=0 USE_ECM=0
USE_LAPACK=0 USE_GRAPHICS=0` against a poisoned `mpfr.h`, and the CI smoke test
passes.

## Memoised definitions are linear: a hash index of pattern-free rules ; v0.6023

- **Pattern-free DownValues (`f[1] = ...`, the entries a memoised
  `f[n_] := f[n] = ...` stores) are kept in a per-symbol hash index.** Looking
  one up, or redefining it, no longer scans every stored value.
  - `f[n_] := f[n] = n` over 20000 values takes 0.024 s. It took ~38 s,
    because every call matched against every stored value, and every new
    value rescanned the list.
  - 10000 lookups of stored values take 0.004 s, down from 6 s.
- This relies on pattern-free rules leading the list (v0.6022), and on such a
  rule matching only the expression equal to it.
  - The index is trusted only while it records the current list head, which
    catches Block and the optimisers swapping whole lists. Every removal
    (`Unset`, `Clear`, `DownValues[f] = ...`) drops it.
  - Conditional literal definitions kept side by side fall back to the scan,
    and so do `Flat` and `Orderless` heads.
- Results match the reference on Unset, Clear, Block, `DownValues[f] = ...`,
  conditional literals, list, Rational and Real keys, and Orderless heads.
  Valgrind shows only the startup baseline.

## Definitions are ordered by pattern generality ; v0.6022

- **A new rule goes ahead of a stored one only when the stored pattern is
  more general**, as in the reference. A stored pattern is more general when
  it matches everything the new one matches, and more. This replaces the
  numeric specificity score.
  - Pattern-free definitions (`f[1]`, `f[g[a]]`) come first, in definition
    order.
  - Two patterns, neither of which covers the other, keep definition order,
    for example `f[x_Integer]` then `f[x_?EvenQ]`, or `f[h[x__, y_]]` then
    `f[h[x_, y__]]`.
  - Of two patterns that cover each other the newer goes first (`x_` and
    `x_^n_.`), unless they are the same pattern up to renaming.
- The comparison is structural and conservative. It reads typed blanks,
  sequences, `Repeated`, defaults, alternatives, tests and conditions (which
  narrow the pattern), and nonlinear patterns. When it cannot tell, it keeps
  definition order.
- Every ordering decision in about 100 pattern pairs checked against the
  reference agrees.
- The score had put FeynCalc's `DiracTrick` rule
  `h[b___, G[5], c:G[_[__]].., d___]` ahead of the earlier, incomparable
  `h[b___G, di_G, c__G] /; ..`. `DiracTrickInsideDiracTrace` ID17 and ID29
  pass again.
- A later `p[a_, a_]` now goes ahead of an earlier `p[a1_, b1_]`.

## Together leaves function arguments and symbolic exponents alone ; v0.6021

- **Together combines only through `Plus`, `Times` and powers with a
  rational exponent**, as the reference does. Every other subexpression is an
  opaque kernel.
  - `Together[Gamma[2 - D/2]]`, `Together[f[1/a + 1/b]]`,
    `Together[Abs[1/a + 1/b]]`, `Together[x^(1/a + 1/b)]` and
    `Together[(1/a + 1/b)^n]` are unchanged.
  - Before, the argument was combined too (`Gamma[1/2 (4 - D)]`), and the
    kernel then stopped matching the same kernel written elsewhere.
  - `Together[Sqrt[1/a + 1/b]]` is still `Sqrt[(a + b)/(a b)]`.
- **Together threads over `Unequal`, `Rule`, `RuleDelayed` and the logical
  connectives**, as well as lists, equations and inequalities.
  `Together[1/a + 1/b > 0 && x]` is `(a + b)/(a b) > 0 && x`, and
  `Together[1/a + 1/b -> 1/c]` is `(a + b)/(a b) -> 1/c`.
- FeynCalc `FCFeynmanPrepare`: 9 tests that regressed in v0.6009 pass again.
  Since v0.6009, `FreeQ` sees the `Rational` in `2 - D/2`, so `Factor2` hands
  that sum to Together inside `Gamma[...]`.
- A ratcanon test was vacuous: a declining `RatCanonPrototype[e]` only came
  back equal to `e` because Together rewrote its argument. It now reads a
  declined prototype as `e`.

## A pattern-headed call matches one operand of a Flat call ; v0.6020

- **`g_[y__]` and `_[x_]` now match exactly one operand of a Flat head**, as
  in the reference. They never take a group `h[...]` of several operands.
  - With `ff` Flat and Orderless, `ReplaceList[ff[a[1], b[2], c[3]],
    ff[g_[y__], c[3]] :> g]` is `{}`, and the same rule under `ReplaceAll`
    gives `ff[b[2], {a, {1}}]`.
  - Before, `g` could bind `ff` over `a[1], b[2]`. In a product,
    `q /: q[z_, x_] f_[y__] := ...` tried `f -> Times` over every other
    factor first.
  - FeynCalc's `PairContract` and `DiracTrace` rules have this shape.

## Inexact contagion touches only numeric summands and factors ; v0.6019

- **A machine real in a `Plus` or `Times` now numericalizes only the
  siblings that are numeric quantities**, as the reference does.
  - `1. + Pi + x` is `4.14159 + x`, as before.
  - A non-numeric term keeps its exact coefficients: `1.5 - a` is no longer
    `1.5 - 1.0 a`, and `1.5 + 2 a` is no longer `1.5 + 2.0 a`.
  - `1.5 + a - a` is `1.5`. It was `1.5 + 0.0 a`, a zero term that never
    cancelled.
  - `1.5 (2 + a)` and `1.5 + Sqrt[2] a` keep their exact parts.
- An old test claimed the reference writes `1. + 2 x` as `1. + 2. x`. That
  was never checked, and the reference keeps `1. + 2 x`.

## Factor takes a Gaussian-integer content ; v0.6018

- **`Factor` of a polynomial with Gaussian-integer coefficients** now takes
  its content over Z[i], as the reference does.
  - `Factor[4 I a - 4 I b]` is `(4 I) (a - b)`. It was `4 (I a - I b)`.
  - `Factor[2 I x + 2 I]` is `(2 I) (1 + x)`, where it used to stay
    unfactored.
  - `Factor[(1 + I) a + 2 b]` is `(1 + I) (a + (1 - I) b)`, and
    `Factor[-I a + I b]` is `-I (a - b)`.
- **A product with such a coefficient keeps it** and factors the rest. Before,
  `Factor[-(16 I) (56 - 30 D + 3 D^2) a b]` expanded the product and came
  back as `16 a b (-56 I + (30 I) D - (3 I) D^2)`.
- **FeynCalc:** `DiracTrace` ID53 and ID61 now pass. ID43, ID44, ID56 and
  ID57 still pass; they depend on the product case keeping the orientation.

## Together and Cancel treat indexed variables as variables ; v0.6017

- **`x[3]`, `Momentum[p]` and `Pair[Momentum[p], Momentum[q]]` are ordinary
  polynomial variables** on the FLINT `Together`/`Cancel` path. This covers
  any user head with no builtin whose arguments are atoms or such nodes.
  Before, a single indexed variable sent the whole expression to the classical
  multivariate Euclid.
  - A rational function in `x[1..7]` (FeynCalc `FactorList2`) took ~29 s and
    now takes ~0.02 s.
  - The answer is the one the same fraction gets over symbols, signs
    included. For example `Together[1/(1 - x[1]) - 1/(1 + x[1])]` is
    `-(2 x[1])/(-1 + x[1]^2)`, and `E^x[1]/(1 + E^x[1]) + 1/x[2]` now
    combines.
  - The fresh variables are named to sort where the atoms sort canonically, so
    FLINT's sign normalisation agrees with the symbol case.

## Times: no loop on numeric powers, and the reference's merged-exponent sign ; v0.6016

- **Fixed an endless loop through `Times`.** The v0.6008 coprime-basis rule
  also fired when the shared factor was only between two numeric powers.
  `17 Sqrt[17]` became `17^(3/2)`, which evaluates straight back. So any
  product holding such a pair, for example a DSolve residual at
  `x = 23/10`, hit `$RecursionLimit::reclim` and left `Hold[...]` debris.
  The rule now needs a symbolic exponent on at least one side of the shared
  factor.
- **Opposite numeric exponents merge**, as in the reference:
  `2^Sqrt[2] 3^-Sqrt[2]` is `(2/3)^Sqrt[2]`, `2^Pi 3^Pi` is `6^Pi`,
  `2^I 3^-I` is `(2/3)^I`, and `23^(-e) 10^e` is `(10/23)^e`. Integer,
  rational and machine-real exponents are still left to the radical fusion.
- **The merged exponent's sign follows the reference.** A sum keeps the sign
  whose last term is negative, where Mathilda used to read the first term:
  `2^(1 + a) 3^(-1 - a)` is `(3/2)^(-1 - a)` (was `(2/3)^(1 + a)`), and
  `2^(a - 1) 3^(1 - a)` is `(3/2)^(1 - a)`.
- **Complex coefficients follow the reference too.** In a sum, a last term
  reads as negative when the printer would write it with a minus
  (`-I t`, `(-1 + I) t`). A product flips only for a negative imaginary
  coefficient, so `2^(-I t) 3^(I t)` is `(3/2)^(I t)`. A complex number keeps
  the sign with a positive imaginary part: `2^(-I) 3^I` is `(3/2)^I`.
  Exponents with an inexact number do not merge.
- **Fixed a stack overflow in `Simplify`/`Integrate` (Mathar M11338).**
  `RadicalCanon` splits `(4/5)^(5/8 - I t)` into `4^(5/8 - I t) 5^(-5/8 + I t)`.
  With the last-term rule but no complex case, the merge wrote that back as
  `(5/4)^(-5/8 + I t)`, and the two forms alternated until the stack ran out.

## ToExpression of a non-string ; v0.6015

- **`ToExpression` now handles a non-string argument as the reference does.**
  An atom is its own value: `ToExpression[4]` is `4` and `ToExpression[x]`
  is `x`. Any other expression gives `ToExpression::notstrbox` and `$Failed`.
  With a format type, a non-string gives `ToExpression::notstr` and stays
  unevaluated. Before, every non-string stayed unevaluated.
- **FeynCalc:** this is `DiracTrace-ID7`.

## ReleaseHold releases a held head ; v0.6014

- **`ReleaseHold` now strips one layer of `Hold` (and `HoldForm`,
  `HoldComplete`, `HoldPattern`) at every position, heads included**, as the
  reference does. `ReleaseHold[Hold[f][x]]` is `f[x]` (it was left as it was),
  and `ReleaseHold[Hold[Hold[f]][x]]` is `Hold[f][x]`.
- **FeynCalc:** this fixes 7 of the 13 `ToFCPartialFractionForm` failures and
  removes the first blocker in 5 more. Its `FRH` releases the
  `Hold[Coefficient][...]` calls it builds. The rest wait on `Apart` with
  radical or `I` linear factors.

## D of a compound head ; v0.6013

- **`D` now differentiates through a compound head**, as the reference does.
  `D[g[a][x], x]` is `Derivative[1][g[a]][x]`, by the same chain rule as for
  a symbol head. It used to stay unevaluated.
- **A head that depends on the variable** adds the derivative through the
  head, applied to the arguments: `D[g[x][x], x]` is
  `Derivative[1][g[x]][x] + Derivative[1][g][x][x]`.
- **FeynCalc:** all 18 `FCLoopGLIDifferentiate` failures. It differentiates
  `GLI[topo, {..}][m]` and then looks for the `Derivative[1][GLI[...]]` heads.
- **Inactive integrals and held expressions.**
  - An inactive integral over a non-list variable now differentiates by the
    reference's Leibniz form: `D[Inactive[Integrate][f[u], Sqrt[x]], x]` is
    `f[u]/(2 Sqrt[x])`. It used to stay inert.
  - Other inactive integrals stay inert, and so does a held expression:
    `D[Hold[x], x]` was `Derivative[1][Hold][x]`.
- **`Factor` of a rational expression** now factors the numerator and the
  denominator with the FLINT multivariate factoriser that a direct
  `Factor[poly]` uses. The classical path had taken ~50 s on a 7-variable
  FeynCalc case.

## Internal`SyntacticNegativeQ reads sums and complexes as the reference does ; v0.6012

- **A sum is now read by its first term**, so `-a - b` and `-1 + x` are
  `True` and `x - y` stays `False`. A sum used to be always `False`.
- **A complex number is now read by its imaginary part alone**:
  `Complex[-1, 2]` is `False` (it was `True`), and `Complex[1, -2]` is `True`.
- **FeynCalc:** this fixes 2 more `SUNSimplify` failures.
  `colorFactor[a] /; SyntacticNegativeQ[a] :> -colorFactor[ExpandAll[-a]]`
  never fired on a negative sum, so the colour factor stayed unexpanded.
- **Mathilda's own caller is unaffected.** `MinusSignQ` in the special-function
  integrator already tests a sum's first term itself.

## OptionsPattern in any position ; v0.6011

- **`OptionsPattern[]` now matches when it is not the last pattern element.**
  It takes a leading run of option arguments, longest first and down to none,
  and leaves the rest to the later elements, as in the reference. Before, it
  took every remaining argument and failed on any that was not an option, so
  `MatchQ[t[x], t[OptionsPattern[], a_]]` was `False`.
- **The `Orderless` case.** On an `Orderless` head the slot sorts first, so
  `SetAttributes[s, Orderless]; s[x, y] /. s[args__, OptionsPattern[]] :> ...`
  never matched. That was a silent wrong value.
- **FeynCalc:** this was 10 of the 17 `SUNSimplify` failures. `SUND` is
  `Orderless`, and both its "unique coloured objects" step and its own
  DownValues are written this way.

## A condition does not reorder a definition ; v0.6010

- **DownValue order no longer promotes a conditioned rule.**
  - Each condition layer used to add to a rule's specificity score, so
    `f[p[a1_, b1_]] := "gen" /; True` was tried before an earlier
    `f[p[a_, a_]] := "spec"`.
  - A rule written `rhs /; c1 /; c2` jumped ahead of ones with a single
    condition.
  - In both cases a different rule fired, with no message: a wrong value.
- **Conditions and pattern tests (`x_?test`) are now neutral, as in the
  reference, wherever they sit in the pattern.** Between two rules that are
  the same once the guards are removed, the guarded one still goes first:
  `g[x_] := 1; g[x_ /; x > 0] := 2` tries the guard first.
- **FeynCalc:** this was all 28 `FromGFAD` failures. `fromGFAD`'s eikonal rule
  `... /; c1 /; c2` had moved ahead of the square-completion rules.

## Rational and Complex numbers are atoms to rules and searches ; v0.6009

- **Replacement rules no longer reach inside a number** (a wrong value until
  now). This covers `ReplaceAll`, `ReplaceRepeated` and `Replace` at any level:
  - `{1/2} /. 2 -> 3` was `{1/3}`, and `{1/2} /. 1 -> 5` was `{5/2}`.
  - `{1/2} /. Rational -> f` was `{f[1, 2]}`, and `{I} /. Complex -> h` was
    `{h[0, 1]}`.
  - All of these now stay as they are, as in the reference. A rule for the
    whole number (`Rational[a_, b_] -> ...`) still applies.
- **`Cases`, `Count`, `Position` and `DeleteCases` treat a number as an atom.**
  `Count[{1/2}, 2, Infinity]` is `0` and `Position[{I}, Complex]` is `{}`.
  `DeleteCases[{1/2}, 2, Infinity]` used to corrupt the number into
  `Rational[1]`.
- **`FreeQ` and `MemberQ` now see a number's head at the number's own level**
  when heads are included. `FreeQ[I x, Complex]` and `FreeQ[f[1/2], Rational]`
  are `False`, and `MemberQ[f[1/2], Rational, {1}, Heads -> True]` is `True`.
  `FreeQ` keeps `Heads -> True` with an explicit level spec.
- **FeynCalc:** its `MomentumCombine` gates its complex-momentum step on
  `FreeQ[expr, Complex]`. All 16 `FCLoopSwitchEtaSign` failures were this.
- **`Limit` rejects a number as its variable**, with `Limit::ivar`, as the
  reference does. `Block[{x}, x = 5; Limit[Sin[x]/x, x -> 0]]` used to answer
  `0`, and then `1` once `/.` stopped rewriting inside `1/5`.
- **Exposed: a test of real-form Risch output was vacuous.** The check
  `FreeQ[g, Complex]` behind it never saw complex numbers, so it always passed.
  It now shows that `1/(3 + 5 Cos[x])` still integrates to complex-argument
  logs. That case is asserted for correctness only until the real
  reconstruction handles it.

## Times: numeric powers over a coprime basis ; v0.6008

- **When an exponent is symbolic, `Times` now writes numeric powers whose
  bases share a factor over one coprime basis**, as the reference does.
  - `4^a 6^b` is `2^(2 a + b) 3^b`, and the coefficient is absorbed:
    `12 2^n` is `3 2^(2 + n)` and `4^a/2` is `2^(-1 + 2 a)`.
  - Equal exponents merge first (`2^a 8^a` is `16^a`), and
    `(2/3)^a (9/4)^b` is `(2/3)^(a - 2 b)`.
  - The basis comes from gcds alone, so FeynCalc's products of huge prime
    powers collapse with no factoring.
  - All 16 probes match the reference.
- **The O3 split now reads bignum rationals.** Its sign test had looked only at
  `int64` rationals, so `(p/N^4)^a` was not split when `N^4` was a bignum.

## Simplify: exponent normal form and a cross-term coprime basis ; v0.6007

- **Equal exponents and arguments, written differently, now cancel.**
  `Simplify[a^(3 (-1 + e)) - a^(-3 + 3 e)]` and
  `Simplify[g[2 (1 + e)] - g[2 + 2 e]]` are `0`, as in the reference. Before
  and after the search, two compound exponents (or ordinary-head arguments) in
  the same place that agree after `Expand` both take the factored expansion.
  An exponent whose expansion is strictly smaller is expanded:
  `Simplify[la^2 (la^2)^(e - 1), la > 0]` is `la^(2 e)`, where it was
  `la^(2 + 2 (-1 + e))`.
- **Numeric powers across the whole expression are written over one coprime
  basis** (gcds only), with each basis power held as an opaque generator while
  the search runs. Terms that are one power family in different clothes then
  cancel. FeynCalc's `FactorList2` check, a sum of products of random-prime
  powers, is now `0`, and `FactorList2` ID6 now passes.

## Powers with a symbolic exponent as polynomial generators ; v0.6006

- **`Variables`, `Factor` and `FactorList` read `b^(n + k t)` as
  `b^n (b^t)^k`**, as the reference does (`src/poly/expsplit.c`).
  - `Variables[x^(1 + e) + x^(2 + e)]` is `{x, x^e}`.
  - `Factor[x^(2 + e) - x^e]` is `(-1 + x) x^e (1 + x)`.
  - `FactorList[(x + y)^(-3 + 3 e)]` is `{{1, 1}, {(x + y)^e, 3}, {x + y, -3}}`.
  - Each power was previously one opaque atom: `Factor` and `FactorList`
    left such sums unfactored, and `Variables` listed `x^(1 + e)` itself.
- **How it works.** Each `b^t` becomes a private symbol, the builtin runs on
  the rewritten input, and the generators go back in (`K^k -> b^(k t)`).
  - An integer coefficient of `t` is the generator's degree. A non-integer one
    keeps its term whole (`x^(e/2)`).
  - A numeric base is a constant to `Variables`, as there.
- **Results.**
  - The 14 new expectations are identical to the reference's output.
  - FeynCalc's `FactorList2` ID7, ID8 and ID11 now pass.
  - ID5, ID6 and ID10 still need `Simplify` to normalise exponents
    (`a^(3 (-1 + e)) - a^(-3 + 3 e)`).
